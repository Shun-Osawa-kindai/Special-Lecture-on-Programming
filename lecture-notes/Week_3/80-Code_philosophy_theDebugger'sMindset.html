Weekly Philosophy

デバッガーのマインドセット
「The Debugger's Mindset」

バグの修正は、プログラマーのキャリアのあらゆる段階で発生します。実際、プログラマーはコードを書く時間よりも、デバッグを行う時間の方がはるかに長いと言われています。

バグに出会ったとき、私たちはどのように思考を切り替え、探偵のように問題を解き明かしていけばよいのでしょうか。

The Debugger's Mindset Slide 1 / 9
Perspective Shift

Architect vs. Detective

「建築家」から「探偵」への視点切り替え

コードを書くとき：建築家（Architect）

理想の仕組みを構想し、設計し、構築していく創造的なモード。

デバッグするとき：探偵（Detective）

事実を観察し、仮説を検証し、現場（コード）で起きた出来事を調査するモード。

最大の難関：バグが発生した瞬間こそ、最も「建築家」の執着を捨てて「探偵」の冷徹な観察眼へ切り替えることが難しい瞬間です。だからこそ、作法が必要になります。
The Debugger's Mindset Slide 2 / 9
Initial Steps

First Response

① 一呼吸置く ＆ ② エラーを読む

ステップ1：まずリラックスする（Relax）

無意識のうちに焦ってコードをいじり回すと、かえって事態が悪化します。一度PCから離れ、深呼吸をし、お茶を飲むか散歩をしましょう。夜遅くなら、思い切って寝るのが最善です。

ステップ2：エラーメッセージを熟読する（Read the Error）

コンソールを開き、エラーの行番号とメッセージを確認します。現代ならAIに聞くのも手ですが、この講座はプログラミングの基本の基本を学ぶ場です。まずはAIや検索に頼らず、エラー文を自分の目で読んで紐解く練習をしてみましょう！

The Debugger's Mindset Slide 3 / 9
Basic Checks

Checklist & Tidying

③ 基本チェック ＆ ④ コードの整理整頓

基本中の基本を確認（Sanity Check）

  • 編集しているファイルと実行しているファイルは一致しているか？
  • ファイル名や変数名にスペルミスや大文字小文字の間違いはないか？
  • 単にブラウザを再読み込み（リロード）してみたか？
  • カッコの閉じ忘れや関数の引数の数は正しいか？

コードを綺麗に整える（Tidy & Explain）

  • 汚いコードはバグの温床です。インデント（字下げ）を揃えましょう。
  • インデントを整えるだけで、カッコの対応ズレが浮き彫りになります。
  • 意味不明な数字（マジックナンバー）に変数を割り当て、注釈（コメント）を書き加えましょう。
// Before: インデント不統一 + マジックナンバー直書き
if (distance < 120)
{
showHint = true;
if (isReady)
{
drawRobot();
}
}

// After: Allman + 変数化で読みやすく安全
var treasureRadius = 120; // マジックナンバーに名前を付ける
if (distance < treasureRadius)
{
  showHint = true;
  if (isReady)
  {
    drawRobot();
  }
}

Terminology

Academic Notes

Allman と Magic Number の由来

Allman Style（オールマンスタイル）

C言語系プログラマ Eric Allman の名に由来するブレイス配置スタイルです。
{ を次行に置くことで、ブロック境界が縦に揃い、初心者でも構造を目で追いやすくなります。

if (isReady)
{
  drawRobot();
}

Magic Number（マジックナンバー）

由来は「意味不明なのに効いてしまう“魔法の数字”」という皮肉です。
直接数値を書くと意図が消えるため、名前付き変数や定数に置き換えるのが実務の基本です。

// NG
if (distance < 120)
{
  showHint = true;
}

// Better
var treasureRadius = 120;
if (distance < treasureRadius)
{
  showHint = true;
}

Problem Definition

Isolate & Verbalize

⑤ 問題の言語化 ＆ ⑥ 変化点の特定

アヒルちゃんに話しかける（Rubber Duck Debugging）

「いま何をしていて、何が起きているか」を机の上のアヒルちゃん（ラバーダック）に声に出して説明してみましょう（ラバーダック・デバッグ）。言葉にするだけで自分の思考の矛盾に気づくことが多々あります。基本はアヒルちゃんで、どうしても行き詰まった時や機会がある時は、友人や先生に相談してみましょう！

「直前に変更したこと」は何か？（What Did You Change?）

すべての変更はバグの潜在的な原因です。直前に加えた変更こそが、直面している問題の最大の容疑者です。

The Debugger's Mindset Slide 6 / 9
Safe Testing

Safe Refactoring Protocol

⑦ バックアップ ＆ ⑧ 1つずつの最小変更

コードを書き換える前の「絶対ルール」

推測でコードを直そうとする前に、必ず現在の状態のバックアップ（複製）を取りましょう。二次災害を防ぎます。

一回につき一箇所だけ試す

一度に複数の変更を加えると、何が効いたのか分からなくなります。1箇所変えてテストし、治らなければ即座に元へ戻すのが鉄則です。

値のプリント出力（console.log）

変数に期待通りの数字が入っているか、コンソールに出力して目視で確認します。一度に出力しすぎると混乱するため、数個に絞りましょう。

// 例：クリック時の値を最小限だけ確認する
function mousePressed()
{
  var d = dist(mouseX, mouseY, treasureX, treasureY);
  console.log("mouse:", mouseX, mouseY);
  console.log("distance:", d);
}
The Debugger's Mindset Slide 7 / 9
When Still Stuck

Break the Loop

最強の問題解決者は、休憩と睡眠

1. 積極的に休憩・睡眠を取る

脳が疲れていると、同じバグを見落とし続けます。10分散歩、短い仮眠、しっかり睡眠を「戦略」として使いましょう。翌日あっさり解けるのはよくあることです。

2. 友人や先生に相談する

休憩しても詰まるときは、アヒルちゃんの次の手として相談です。人に説明する過程で、論理の抜けが自分で見えることが多いです。

3. 小さく作り直して再検証する

根本方針がずれている場合は、最小構成で書き直して再確認します。全部を一気に直すより、最小単位で再構築する方が早く安定します。

Weekly Mantra

デバッグを楽しめるようになろう

This Week's Mantra

"Time spent debugging is never time wasted."

（デバッグに費やした時間に、無駄な時間など一つもない）

長時間の探偵作業の末にバグを解決した瞬間、あなたは「歓喜、達成感、安堵」を味わい、そして確実に前よりも深くコードを理解した「学び」を得ています。デバッグのプロセスそのものを楽しみましょう。
