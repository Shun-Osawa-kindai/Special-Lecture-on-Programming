この資料の読み方

「現状」と書いた部分は、今回配布するソースに実装されている動作です。「追加要求の例」は、まだ実装していない候補です。図や表の説明用データを、起動時に自動で入る初期データとは扱いません。

アプリの全体像

利用者はアカウントを作成してログインし、自分の「やること」を登録・検索します。検索結果のボタンで、完了と未完了を切り替えられます。初回のDBには、アカウントやToDoのサンプル行は入っていません。

場所このアプリでの仕事主なファイル
ブラウザHTMLを表示し、入力をフォームとして送る。結果のHTMLを受け取って表示する。templates/が作るHTML、static/style.css
Flaskの処理URLに対応する関数を選び、ログイン状態・入力・対象ユーザーを確認してSQLを実行する。app.py
SQLiteとDBファイル表の記録を読み書きし、確定した値をファイルに残す。instance/todo.sqlite3

ブラウザとFlaskの間はHTTPでやり取りします。FlaskからSQLiteへはPythonのライブラリを呼び出します。この構成でSQLite専用のWebサーバーを起動する必要はありません。

このアプリの画面操作はHTMLフォームを使います。ブラウザ側のJavaScriptやJSON APIを使う別構成の図は、補足資料の例として読んでください。

コードで確かめる

app.py の database()、各ルートの関数、security_headers()を参照します。後者の設定には script-src 'none' があります。HTMLの共通部分は templates/base.html です。

現在のER図とテーブル一覧

アプリが定義している表は三つです。ER図の線は、子の表の user_id が users.id を参照する関係を示します。

表一行が表すもの主な利用場面
users一つのアカウントアカウント作成、ログイン、現在のユーザー確認
login_sessions一つのログイン状態をサーバーで照合する記録ログイン、要求ごとの確認、ログアウト
todos一人が登録した、一つのやること登録、検索、完了状態の切り替え

二つの関係を読む

todos.user_id → users.id：一人のユーザーはToDoを0件以上持てます。各ToDoには、その所有者を示す user_id が必要です。

login_sessions.user_id → users.id：一人のユーザーには、ログイン状態の記録が0件以上対応します。複数回のログインで、同じユーザーに複数の行ができる場合があります。

参照関係と、操作の許可

外部キーは、参照先のユーザーが存在することを確かめる仕組みです。「自分のToDoだけを検索・変更する」という条件は、アプリのSQLにある user_id = ? で指定しています。ER図の線だけで、この操作の制限まで実現するわけではありません。

SQLite内部の表について

AUTOINCREMENTを使うため、SQLiteが内部で管理する sqlite_sequence もあります。上の三つは、教材アプリ自身が定義する表です。内部の表を、利用者のデータモデルへ追加する必要はありません。

users：アカウントの3列

列・意味DBでの宣言アプリの処理・条件
id
アカウントの識別子		INTEGER PRIMARY KEY AUTOINCREMENT登録時のINSERTでは指定せず、SQLiteに採番を任せる。
username
ログイン名		TEXT NOT NULL UNIQUE COLLATE NOCASE前後の空白を除き、英数字と _ の3〜30文字かを確認する。DBの一意性の比較には大文字・小文字を区別しない指定がある。
password_hash
照合用の保存値		TEXT NOT NULL入力パスワードは8〜128文字。保存前に password_security.py でsalt付きscryptハッシュを作る。平文パスワードの列はない。

login_sessions：ログイン状態の3列

列・意味DBでの宣言アプリの処理・条件

列・意味DBでの宣言アプリの処理・条件

ToDoの識別子		INTEGER PRIMARY KEY AUTOINCREMENT登録時はSQLiteに採番を任せる。検索結果に実際のIDが表示される。
user_id

やることの内容		TEXT NOT NULL前後の空白を除き、1〜120文字かを確認する。画面にも required と maxlength がある。

created_at
作成時刻		TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP登録時はDBの既定値を使う。完了状態を切り替えても、この値を更新する処理はない。

なぜ登録後にもう一度GETがあるのか

成功時の redirect(...) は、配布版では302の応答を返します。通常のブラウザ操作では、指定先をGETして画面を表示します。追加後の遷移先は登録画面です。保存した項目を確認するには、利用者が「やることの検索」へ移動します。

一つの値を追う

登録：titleとcsrfをPOSTする

  1. add.html の name="title" の入力欄へ「SQLを試す」と入力します。
  2. フォームは POST /todos/add で title と、画面に埋め込まれた csrf を送ります。csrfは利用者が手入力する値ではありません。
  3. add_todo() はフォームを確認し、request.form.get("title", "").strip() で内容を受け取ります。
  4. 条件を満たすと、本人のIDと内容を INSERT へ渡し、commit() します。
  5. 登録画面へ戻ります。「やることの検索」を開き、追加した内容と実際のIDを確認します。
title = request.form.get("title", "").strip()
database().execute(
    "INSERT INTO todos (user_id, title) VALUES (?, ?)",
    (g.user["id"], title),
)
database().commit()

上の抜粋の前後には、ログイン・CSRF・文字数の確認と、表示・遷移の処理があります。? の位置に渡す値は、SQLの文字列と別に指定されています。

空白だけ、または120文字を超えるタイトルは保存せず、メッセージを表示して登録画面を返します。この入力エラーの処理と、CSRFの検証に失敗したときの400応答は区別してください。

検索：qをGETのクエリ文字列で送る

search.html の検索フォームはGETです。たとえば「SQL」で検索すると /todos/search?q=SQL へ要求します。入力欄の名前は q、Pythonの受け取りは request.args.get("q", "") です。

SELECT id, title, completed, created_at FROM todos
WHERE user_id = ? AND title LIKE ? ESCAPE '\'
ORDER BY id DESC LIMIT 100

SQLへ渡す前に、検索語の前後の空白を除き、120文字までにします。%、_、\にはエスケープ処理があり、利用者が入力した記号をそのまま文字として探せるようにしています。検索結果は本人の記録から最大100件、新しいID順です。空の検索語は、本人の記録を最大100件表示します。

GETとPOSTで、入力を受け取る場所が違う

検索語 q は request.args、登録内容 title とフォーム確認用の csrf は request.form から読みます。この対応を、HTMLとPythonの両方で確認してください。

完了切り替え：IDと本人の条件を使う

UPDATE todos
SET completed = CASE WHEN completed = 1 THEN 0 ELSE 1 END
WHERE id = ? AND user_id = ?

URLから受け取ったToDoのIDと、ログイン中ユーザーのIDを使います。処理は「指定した完了値にそろえる」ではなく、保存済みの状態を反転します。続けて二回実行すれば、0から1、1から0へ変わります。

完了切り替え後は、検索語を付けずに検索画面へ戻ります。「検索条件を保ちたいか」は、第11回以降に利用者の目的から考えられる要求の一例です。

ログインを支える処理を分けて読む

第9・10回では、登録・検索・更新の流れを先に追えれば十分です。認証の詳細を調べたいときは、次の役割から読み始めてください。

担当役割読み始める関数
password_security.py登録時はsalt付きscryptハッシュを作り、ログイン時は保存済みの値を用いてパスワードを照合する。hash_password_for_storage()
password_matches_stored_hash()
auth_rsa.pyログイン状態を表すトークンに秘密鍵でRSA署名し、公開鍵で署名と有効期限を確認する。load_keys()
create_token()
verify_token()
app.pyトークンの検証に加え、DB内のセッションとユーザーを照合し、処理対象を決める。load_current_user()
login_required()
check_csrf()

このアプリのRSAは署名に使っています。 トークンの内容を読めないように暗号化する処理ではありません。パスワードの保存には、別のscryptハッシュを使います。sid_hashを作るSHA-256も、パスワード保存の処理とは別です。

POSTフォームには csrf を埋め込み、サーバー側で確認します。自分の記録だけを扱うSQL条件、パスワード照合、署名検証、CSRF確認は、それぞれ役割の違う処理です。

二つのCookieの役割

認証用の lesson_auth には、この教材独自のRSA署名付きトークンを入れます。Flaskの session は、未ログイン時のフォーム確認情報や通知にも使われています。instance/flask_secret.key はFlask側の署名鍵で、instance/keys/ のRSA鍵ペアとは別です。この資料には、鍵・Cookie・ハッシュの実値は載せません。

学内の演習には教材専用のアカウント情報を使います。詳しい説明は PASSWORDS_AND_RSA.md にあります。

CREATE TABLE IF NOT EXISTSの意味

表が既にある場合、このCREATE文を変更して再起動しても、その表へ新しい列は追加されません。既存データを保つなら、構造を移す手順を別に考えます。新しい練習用DBから始める場合も、残したいデータを確認し、初期化とは別の意思決定にしてください。

第10回の小変更：未完了だけを検索する

search_todos() のWHERE条件に AND completed = 0 を加えます。既存の user_id、検索語の処理、ORDER BY、LIMITを保ちます。検索結果に出さないことと、保存行を削除することは異なります。

変更するSQLの例
SELECT id, title, completed, created_at FROM todos
WHERE user_id = ? AND title LIKE ? ESCAPE '\'
  AND completed = 0
ORDER BY id DESC LIMIT 100

これは未完了だけを常に表示する最小例です。第11回以降には、常に絞るか、利用者が切り替えるかも要求として検討できます。

起動・再起動・観察

Cloud Shellで起動する

配布一式を展開し、アプリのフォルダを作業場所にします。

cd flask_sqlite_rsa_starter
bash start.sh

start.shは仮想環境と必要ライブラリを準備して、8080番で起動します。ウェブプレビューの8080番を開きます。初回のライブラリ導入にはネットワーク接続が必要です。

アカウントを作成してログインし、登録画面で二つのToDoを追加します。検索画面で実際のIDを記録し、一つだけ完了にしてください。固定のID番号と一致させる必要はありません。

再起動して、同じ記録を探す

  1. 現在のユーザー名、登録したタイトル、表示されたIDを控えます。
  2. サーバーのターミナルで Ctrl+C を押して停止します。
  3. 同じフォルダで、もう一度 bash start.sh を実行します。
  4. 必要なら再ログインし、検索で同じToDoと完了状態を確認します。

通常の再起動はDBと鍵を保持します。ログイン期限が切れても、ToDoが消えたという意味ではありません。このアプリには --inspect や --reset という起動オプションはありません。

ローカルPCで起動する場合

Python 3.10以上を用意します。以下はmacOS／Linuxの例で、アプリのフォルダ内で実行します。

python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
COOKIE_SECURE=0 .venv/bin/python app.py

http://127.0.0.1:8080 を開きます。Cloud ShellのHTTPSプレビュー用 start.sh は COOKIE_SECURE=1 を設定するため、ローカルHTTPでは上の起動方法を使います。

WindowsのPowerShellでは次のように指定できます。

py -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:COOKIE_SECURE = "0"
.venv\Scripts\python.exe app.py

読み取り用SQLの例

同じDBを開いた観察用の環境で使う例です。ユーザー名・鍵・パスワードハッシュなどの実値を共有する必要はありません。

SELECT id, user_id, title, completed, created_at
FROM todos
ORDER BY id;

これはDB内の全ToDoを読む観察用SQLです。Web画面の検索では、本人に限定する user_id = ? も付いています。アプリ用DBの保存先は instance/todo.sqlite3 です。bookの練習用DBと取り違えないでください。

付属テストを実行する

依存ライブラリを準備したPython環境で、アプリのフォルダから実行します。

python -m unittest discover -s tests -v

仮想環境を有効化していない場合は、その環境のPythonを直接指定します。付属テストは各テスト用の一時DBで、登録・ログイン・ユーザーごとの分離などを確認します。自分の変更については、要求から決めた期待結果も別に記録してください。

自分で説明できるか

  1. タイトルの入力から保存まで、HTMLのname、Pythonの受け取り、SQLの列を指し示す。
  2. ToDoのIDとユーザーIDの役割を区別する。
  3. 現在値から分かることと、履歴がなければ分からないことを一つずつ挙げる。
  4. 一つの変更要求について、確認するファイルと、実行後に見る値を説明する。
